# 象信 AI 前置闸门 —— 临床数据雷达接入说明

**日期**：2026-11-25
**改动范围**：新增 `src/xiangxin_gate.py`、`src/score.py`、`config/scoring.yaml`、`.github/workflows/radar.yml`

---

## 一句话

象信**不替代** LLM 打分，而是做 LLM 前面的闸门：拦掉明显不是临床内容的条目
（纯 BD / 人事 / 融资 / 行业综述 / 会议预告 / 财经股价），省 LLM 调用。

---

## ⚠️ 判据与另外两个雷达【完全不同】，不要照搬

这是本雷达接入时最容易犯、后果最严重的错误：

| 雷达 | 闸门问的问题 |
|---|---|
| pharma-bd-radar | 「有没有交易对手方」 |
| clinical-data-radar（本雷达） | 「有没有具体的临床试验结果或关键节点」 |
| pharma-policy-radar | 「是不是官方机关发出的、对行业有约束力的文件」 |

**照搬 BD 的判据会把临床读出全拦掉**——BD 判据里「临床数据读出」明确列为「非交易」。

### 本雷达「是临床」必须包含的 7 类（少列一类可能整条产线归零）

1. 临床试验结果读出（达到/未达到终点、疗效数据、安全性数据、统计显著性结论）
2. 试验终止、暂停、失败、被撤回
3. 关键进展节点（入组完成/启动、期中分析、注册试验启动）
4. **监管审批与上市申请** —— ⚠️ 本雷达明确把审批作为临床进展的结果
5. 学术会议上的逐研究读出（含摘要号的研究报告）
6. 药物警戒/安全性事件（不良事件、召回、警示）
7. 与具体临床项目直接相关的研发进展（新药获批临床、适应症扩展获批）

> 第 4 类是最危险的：把「获批」当成非临床，会把本雷达的正常产出拦掉一大块。

---

## 改了什么

### 1. 新增 `src/xiangxin_gate.py`

独立模块，只做一件事：判断「这条是不是临床内容」。

| 做什么 | 怎么做的 |
|---|---|
| 拦掉非临床条目 | Choice 问题「是不是临床试验结果或关键节点」，置信度 ≥ 0.80 且答案是「非临床」才拦 |

**安全边界（全部实测过）**：

- 无 `XIANGXIN_API_KEY` → 全部放行
- 没装 `xiangxin-sdk` → 全部放行
- key 无效（401）→ **整体旁路**，只打一次请求就退出，不浪费 401
- 单条失败 → 只放行那一条，其余继续
- **空 state（标题/摘要/正文全空）→ 不判，直接放行**（见下方 bug 记录）
- 配置关闭 → 完全不生效

### 2. `src/score.py`

`score_items()` 里接闸门，在 `_prefilter` 之后、送 LLM 之前。

### 3. `config/scoring.yaml`

新增 `llm.xiangxin_gate.enabled`，**默认 true**。

## 🐛 踩过的坑：空 state 被误判成「非临床」（已修）

**这是本次接入最重要的发现，也是三个雷达共有的隐患。**

### 症状

首次回归测试（43 天历史数据，4085 条）报出 **10 条漏杀**，
其中 4 条是真实临床读出：

| id | score | flags | 标题 |
|---|---|---|---|
| `6bed09b0cc4ff6a4` | 6.7 | `['met']` | （标题空） |
| `ae983f23fdb58df` | 6.9 | `['met']` | （标题空） |
| `c1159daa1e770f05` | 6.9 | `['halted']` | （标题空） |
| `5ec8892289979d3` | 7.4 | `['met','single_arm','surrogate']` | （标题空） |

### 根因

这 10 条的 `title` / `summary` / `content` **全部为空**——正文抓取失败时只剩 `id`。

送进象信时 state 长这样：

```python
{"标题": "", "摘要": ""}
```

**两个空字符串**。象信没有任何文本可判，只能猜——而它**一律猜成「非临床」**。

> 这跟 skill 里记的头号故障是同一类问题：**素材是空的，模型就用世界知识编**。
> 闸门这层，"编"出来的结论是"这不是临床的"，于是真实读出被误杀。

### 修法

加 `_has_text()`：**没有文本就不判，空条目直接放行给 LLM**。

```python
if not _has_text(it):
    stats["no_text"] = stats.get("no_text", 0) + 1
    passed.append(it)
    continue
```

理由：空条目反正也拿不到素材（compose 阶段的 `material_is_thin` 会拦），
但**至少不会在闸门这层被误杀成"非临床"**。

### 同源隐患已同步修复

- `pharma-policy-radar/src/xiangxin_gate.py` —— 同样的修法
- `pharma-bd-radar/src/xiangxin_gate.py` —— 同样的修法
  （BD 雷达 2295 条历史数据里有 6 条空 state，当时没造成漏杀，
  但那是运气不是设计，换一天数据就可能中招）

> **教训：任何交给模型判断的闸门，都必须先确认"有东西可判"。**
> 空输入 + 模型 = 必然误判，且误判方向由模型的默认猜测决定。

## 实测数据

### 漏杀验证（最关键的指标）

43 天历史数据，4085 条。正例按 LLM 打分划线。

| 阈值 | 漏杀 |
|---|---|
| score ≥ 7.0 | **0** |
| score ≥ 6.5（生产 keep 线） | **0** |
| score ≥ 6.0 | **0** |
| score ≥ 5.0 | **3** |

拦截 1154 条（28.2%），空 state 跳过 22 条。

### 修复前后对比

| | 拦掉 | score≥5.0 漏杀 | score≥6.0 漏杀 |
|---|---|---|---|
| 修复前 | 1176（28.8%） | **10** ❌ | **4** ❌ |
| 修复后 | 1154（28.2%） | **3** ✅ | **0** ✅ |

修复前那 10 条漏杀里，**4 条是 score≥6.0 的真实读出**
（`endpoint_verdict=met` / `halted`），修复后归零。

### 剩下 3 条 score≥5.0 的漏杀——是 borderline，不是 bug

| 条目 | score | flags | LLM 自己的理由 |
|---|---|---|---|
| Cell论文：AI 设计 IL-21 模拟物… | 5.0 | `preclinical` | "仅有动物数据，无法推断人体疗效，故给5.0分" |
| 近五年小核酸药物研发失败管线复盘 | 5.3 | — | "属于项目级回溯而非单项试验统计结论" |
| 同上（另一天转载） | 5.5 | — | 同上 |

这三条**闸门拦掉是对的**：一条是临床前动物实验，一条是只汇总项目数量与
失败率的**复盘文章**（不含任何单项试验结论）。
LLM 自己也只给了 5.0–5.5 分，远低于 6.5 的生产 keep 线。

判据已相应补充：「临床前研究」算「是临床」（本雷达会评临床前数据，只是降权），
但「复盘/盘点类综述」明确列为「非临床」。

### 集成路径实测

用打桩 LLM 跑真实 `score_items()`：

```
[score] 预筛后 4 条（原始 4）
[xiangxin-gate] 拦掉 1/4（25.0%）非临床条目，剩 3 条送 LLM
```

4 条样例（临床读出 / 获批上市 / 股价新闻 / 空条目）：
临床读出 ✓ 放行、获批上市 ✓ 放行、股价新闻 ✓ 拦掉、空条目 ✓ 放行（bug 修复生效）。

## 上线建议

**当前默认 `enabled: true`。**

1. 先观察 1–2 天，记录每天的产出条数、≥6.5 条数、≥8.0 条数作基线
2. 重点看：
   - ≥8.0 的条目有没有变少 → 变少说明有漏杀，要调低 `BLOCK_CONFIDENCE`
   - 产出条数有没有异常下跌 → 检查 `[xiangxin-gate]` 日志的拦截率
3. 若 2 天内 ≥8.0 条数完全一致，再长期开启

**回滚**：把 `enabled` 改回 `false` 即可，无需回滚代码。

## 已知局限

1. **拦截率只有 28.8%**，远低于 BD 雷达的 78.5%。
   这是预期的——临床雷达的候选池本来就以临床内容为主，
   真正非临床的条目已经被 `_prefilter` 的关键词表先滤掉一批了。
   闸门在这里是**第二道**过滤，不是唯一一道。

2. **`CLINICAL_SIGNAL` 正则仍有漏判**（skill §1b 记过：标题里一个临床词都没有
   的条目会漏过关键词表）。这正是需要象信这层的原因——
   它能读摘要，判断力比关键词表强。

3. **象信仍不抽数字**。终点结论、效应量、样本量这些仍由 LLM 评。

4. **闸门只判"是不是临床"，不判"是不是该报"**。
   终点有没有达到、是不是 III 期、规模够不够大——全是 LLM 的活。
   闸门管太宽会误杀，本雷达的判据故意列得很全（7 类）就是为了收窄闸门职责。

### 关于 CI 依赖（重要）

`xiangxin-sdk` **没有**写进 `requirements.txt`，而是在 workflow 里单独安装：

```yaml
- name: 安装象信可选依赖
  continue-on-error: true
  run: pip install "xiangxin-sdk>=0.3.2"
```

原因：闸门是可选增强，若把它当必需依赖，一旦 PyPI 抖动装不上，
会连带整条评分链路失败——为一个可能失效的功能引入致命风险不划算。
装不上时闸门退回旁路，雷达照常跑。

### CI 上的密钥

`XIANGXIN_API_KEY` 需要写入 GitHub Secrets。
`radar.yml` 的「LLM 评分」步骤已注入该环境变量。

**没配这个 secret 时闸门会自动旁路，不影响评分**——所以不配也不会出事，
只是闸门不生效。

注意：GitHub Actions 的 workflow 只有 `schedule` 和 `workflow_dispatch` 两种触发，
**没有 push 触发**，所以提交代码不会立刻跑生产。
